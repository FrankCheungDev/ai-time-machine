## 1. 文档目的

本文档建立时，项目已经完成可用的 MVP：10 个章节、8 个交互 demo、中英双语、学习进度、时间线、技术谱系、图源页面，以及覆盖单元、浏览器、视觉和教学正确性的持续集成。当前发布表面与后续扩展状态以第 13 节执行记录和 `ROADMAP.md` 为准。

下一阶段不再以“继续增加 demo 数量”为唯一目标，而是依次解决三个问题：

1. MVP 是否达到可公开发布、可被搜索和分享的产品标准？
2. 新增章节是否能在不扩大重复代码和测试维护成本的前提下持续进行？
3. 项目是否真正帮助学习者建立历史脉络和机制直觉？

本文把后续工作拆成三个可独立发布的里程碑，定义每一阶段的任务顺序、验收标准、质量门禁和决策点。

## 3. 执行原则

1. **先发布验证，再扩大范围。** 先把现有 MVP 变成可访问、可索引、可分享的产品。
2. **注册表作为单一事实源。** 学习顺序、时间线、谱系、首页入口和测试矩阵应尽量从章节注册表派生。
3. **先证明重复，再抽象。** 只有同一种交互模式出现至少三次时，才新增共享原语。
4. **教学真实优先。** demo 可以 scripted 或 illustrative，但必须写清简化边界。
5. **内容声明必须可追溯。** 论文、系统、人物和日期必须绑定可靠来源。
6. **每个里程碑都可独立发布。** 不建立跨多个版本才能工作的长期分支。
7. **保持纯静态边界。** 不引入真实模型调用、API key、后端、数据库或用户系统。

## 5. P0：v1.0.1 发布收口与扩展成本治理

### 5.1 工作流 A：文档与发布基线

任务：

1. 更新 README、中文 README 和 ROADMAP，使其与 10 章、8 demo、双语和学习进度的实际状态一致。
2. 在 Astro 配置中明确正式站点 URL。
3. 为中英文页面补齐 canonical、hreflang、Open Graph 和 Twitter Card 元数据。
4. 增加 sitemap、robots.txt、404 页面和默认分享图。
5. 记录部署平台、预览环境、生产发布和回滚步骤。
6. 决定是否启用隐私友好的匿名分析；未作决定前不引入追踪脚本。

验收标准：

- 每个中英文页面拥有正确的 canonical 和互相对应的 hreflang。
- 首页、章节、时间线、谱系和图源链接可以生成正确分享预览。
- 生产构建可部署，关键路由在预览环境完成 smoke test。
- README 与 ROADMAP 不再包含已完成事项作为“未来计划”。

### 5.2 工作流 B：章节扩展架构

任务：

1. 将超大页面文案模块按章节或页面域拆分，保留统一导出入口。
2. 扩展章节注册表，使首页顺序、学习路径、时间线和谱系关联继续从一个定义派生。
3. 移除 Playwright 中手写的重复章节顺序和路由矩阵，优先使用共享 fixture 或注册表生成的数据。
4. 将综合测试文件按“国际化、学习路径、demo 行为、视觉、教学正确性”拆分。
5. 盘点 Toggle Group、Compare、Slider、Matrix/Grid 等模式；仅对已有三处以上的稳定重复进行抽象。
6. 为“新增一个章节需要修改哪些文件”建立自动化契约测试。

验收标准：

- 中文、英文、移动端、学习进度和现有 demo 行为不变。
- 新章节注册后，首页、学习路径、时间线和谱系不需要分别维护顺序数组。
- 测试失败能够定位到单一领域，不依赖一个超大的综合 spec。
- 所有共享原语都有类型、键盘操作和单元测试。

### 5.3 P0 决策门

以下条件同时满足后，才进入 Safety / Eval 实现：

- v1.0.1 已部署到预览或生产环境。
- 所有 CI 检查通过。
- 章节扩展契约已经稳定。
- Safety / Eval 的教学问题、简化边界和来源已经评审。

## 6. P1：v1.1 Safety / Eval 与图源资产库

### 6.1 Safety / Eval 教学目标

核心问题：

> 当 RAG 和 Agent 能读取外部知识并执行动作后，系统如何发现、阻断和修复风险？

核心交互：

- 切换正常请求与风险请求。
- 沿着红队样本、护栏、权限边界、人工复核和回归评估推进。
- 观察一次失败如何变成可复现测试，并阻止同类问题再次进入发布版本。

可见结果：

- 用户能区分“模型看起来能回答”和“系统经过可重复评估后更可靠”。
- 用户理解 Safety / Eval 是持续反馈回路，而不是上线前的一次检查。

评估维度：

| 维度     | 示例                                   |
| -------- | -------------------------------------- |
| 质量     | 正确性、相关性、引用一致性             |
| 安全     | 提示注入、越权工具调用、有害输出       |
| 鲁棒性   | 边界输入、工具失败、知识冲突、目标漂移 |
| 系统成本 | 延迟、调用次数、人工复核成本           |

历史原型提交 4c1d69a 不在 main，相关本地和远程分支已经删除。若该对象仍可读取，只能作为交互和测试范围的评审参考；正式实现仍需从更新后的 main 新建分支，并重新通过全部门禁。

### 6.2 Safety / Eval 交付清单

- 中英文数据与章节文案。
- Svelte 教学 demo。
- 中英文静态路由。
- 时间线、谱系、首页和学习路径接入。
- 简化说明和至少两类可靠来源。
- 单元测试、交互 smoke test、移动端测试、可访问性测试和教学正确性测试。
- 展示正常状态、风险状态和修复后状态的截图或短录屏。

### 6.3 图源资产库

为现有 8 个 demo 各提供至少一份稳定的可下载 SVG，并提供 PNG 预览。

每个资产记录：

- 资产 id 与标题。
- 对应章节和演示状态。
- SVG 与 PNG 路径。
- 稳定节点/箭头 id 说明。
- 版本、更新时间和许可证。
- 教学简化说明。

验收标准：

- 图源页面不再硬编码单个 RAG 下载卡片，而是从资产清单生成。
- 8 个现有 demo 都有可下载 SVG；Safety / Eval 在发布时同步提供图源。
- CI 校验资产路径、id 唯一性和下载链接。

## 7. P2：v1.2 历史深度与学习效果验证

### 7.1 事件级历史时间线

在保留章节级主线的同时，增加代表性事件层：

- 关键论文、模型、系统和工程突破。
- AI 寒冬、算力与数据变化等范式转折。
- 事件与章节、谱系节点和来源之间的关联。

每个事件至少包含：

- 年份或时间范围。
- 中英文标题和摘要。
- 事件类型。
- 关联章节。
- 至少一个可靠来源。
- 对后续技术的影响。

不以“收录所有事件”为目标；优先选择能解释因果转折的节点。

### 7.2 学习自测

每章增加一个不依赖后端的概念自测：

- 只检验本章核心直觉。
- 反馈解释“为什么”，不只显示对错。
- 不阻断继续学习。
- 本地记录完成状态，并允许清除。

### 7.3 匿名产品指标（当前禁用）

隐私评审只是启用采集的必要条件，不是实施授权。所有者已决定不采用需要付费的 Plausible，当前也没有获批替代 provider；`learningSignalCollectionMode` 在 `main` 上保持 `disabled`，生产 CSP 保持 `connect-src 'none'`。

项目继续保留以下经过评审的站内事件契约，供产品逻辑与测试验证；当前没有 listener 把它们发送出浏览器：

- 章节开始。
- 核心交互完成。
- 自测完成。
- 打开自测解释。
- 继续到下一章。

不采集用户输入正文、个人身份信息或跨站追踪数据。

只有未来另行批准的数据来源积累了真实聚合证据后，以下指标才可用于决策：

- 章节开始到核心交互完成率。
- 完成后继续下一章的比例。
- 自测首次正确率与解释展开率。
- 中文与英文、桌面与移动端之间的明显差异。

## 8. 标准执行流程

### 8.1 任务进入条件

每项工作开始前必须有一个可核验的任务说明，至少包含：

- 要解决的用户问题。
- 本次要教的核心直觉或要改善的产品指标。
- 范围与非范围。
- 参考资料或事实核查要求。
- 可测试的验收标准。

### 8.2 开发准备

按照仓库工作流执行：

    git checkout main
    git fetch origin
    git pull --ff-only origin main
    git worktree add -b codex/<task-name> .worktrees/<task-name> main

主工作区保持在 main，仅用于同步和 worktree 管理。

### 8.3 实现顺序

对内容或 demo 任务，默认顺序为：

1. 更新数据类型和章节/资产注册定义。
2. 编写中英文文案、来源和简化说明。
3. 实现静态结构和交互状态。
4. 接入学习路径、时间线、谱系或图源清单。
5. 添加单元、浏览器、移动端、可访问性和教学正确性测试。
6. 生成截图或录屏并进行人工视觉检查。

### 8.4 验证门禁

提交 PR 前运行：

    pnpm format:check
    pnpm validate:data
    pnpm lint
    pnpm build
    pnpm test

视觉改动还必须在桌面和窄屏状态检查：

- 文本是否溢出或遮挡。
- 控件是否可通过键盘操作。
- 激活节点、箭头和解释是否同步。
- 简化说明和参考资料是否可见。
- 中英文布局是否都成立。

### 8.5 PR 要求

每个 PR 必须包含：

- 改动摘要和对应任务。
- 用户或贡献者影响。
- 验证命令与结果。
- 视觉改动的截图或录屏。
- 新增历史声明的 fact-check 说明与来源。
- demo 的教学简化边界。

默认使用 Draft PR；完成所有门禁和内容评审后再标记为可合并。

### 8.6 评审顺序

1. **产品与教学评审：** 是否只教一个核心直觉，三分钟内能否理解？
2. **事实与来源评审：** 历史声明、日期、论文和系统描述是否可追溯？
3. **交互与可访问性评审：** 键盘、移动端、状态反馈和动态语义是否正确？
4. **工程评审：** 数据契约、重复代码、测试边界和静态构建是否稳定？
5. **发布评审：** 预览环境、分享元数据、资源链接和回滚方案是否可用？

## 10. 风险与控制

| 风险                       | 控制措施                                                         |
| -------------------------- | ---------------------------------------------------------------- |
| 为架构整洁进行过度重构     | 只抽象已出现三次的稳定模式；每个重构 PR 独立且保持行为不变       |
| Safety / Eval 范围失控     | 固定一个风险场景和一个反馈回路，不做完整 benchmark 平台          |
| 历史时间线变成事件堆砌     | 每个事件必须解释一个因果转折并关联章节                           |

| 长期分支与 main 偏离       | 每个任务使用短生命周期 worktree 和独立 PR                        |

## 11. 里程碑完成定义

一个里程碑只有在以下条件全部满足后才算完成：

- 计划内用户价值已经可以在生产或预览环境演示。
- 中英文和桌面/移动端体验一致。
- 格式、数据、类型、构建、单元和 Playwright 检查全部通过。
- 历史声明和来源已经完成 fact-check。
- 简化边界、贡献文档和路线图已经同步。
- 视觉改动有截图或录屏证据。
- 没有遗留仅存在于个人 worktree 或未合并分支的必要资产。
- 下一阶段的进入条件和未解决风险已明确记录。
